# OpenRouter Fallback Rotator — Session Notes (2026-08-29)

Reference update for the openrouter-fallback-rotator skill, captured during a live session where the user asked to rank free OpenRouter backup models by capability (not context length) and to tie the weekly digest crons to the current first backup.

## What changed in this session

1. **Tier config added:** `~/.hermes/openrouter_tiers.json` (capability scores 1-10 per model; defaults for `min_tier_score` and `min_context_length`). User-editable; the rotator reads it every run.
2. **Rotator rewritten:** `~/.hermes/scripts/openrouter_fallback_check.py` now sorts by `tier_score desc` (primary), then `unthrottled`, then `context_length desc` (tie-breaker only), then `created desc`. Filters applied: `min_tier_score=4`, `min_context_length=32000`. Old ranking (context-first, created-second) was removed.
3. **Pin-sync added:** `~/.hermes/scripts/pin_cron_to_first_fallback.py` reads `fallback_providers[0]` and applies `hermes cron edit --model ... --provider openrouter` to the two weekly agent jobs (`fe2333f495f0`, `d9a937ce7f72`). Called from rotator after every successful chain update (`sync_cron_pins()` in `main()`).
4. **Sample results:** The 120B `nemotron-3-super-120b-a12b:free` produced structurally correct HTML (correct CSS, table, marquee) but partial length (~2,230 chars) vs primary `gpt-5.4` full reports (~3.5K + 11K chars, cited sources, complete slate, no fabricated matchups). Confirmed the small model can produce correct output but is not as complete; the user's preference for HTML output over markdown was embedded in the cron job prompt directly.
5. **Key lesson embedded:** The user's idea that "#1 backup" is fixed — it's not; it changes when the rotator updates. The cron's `model=` pin must either be updated by the sync (current design) or unpinned (user's final choice after testing).

## Pitfalls discovered in this session (should live in SKILL.md)

- **Context length ≠ capability.** A 1M-context small model (`inkling-small:free`) can score lower and get excluded, while a 256K-context 120B model (`nemotron-3-super`) scores 9 and makes the chain.
- **The user's "backup #1" is `fallback_providers[0]`, not a fixed model.** If the rotator demotes the current #1, a static pin in the cron will stay on the old model (which might have been removed/deprecated). The `pin_cron_to_first_fallback.py` mechanism solves this.
- **The free OpenRouter pool changes daily.** Only 18 `:free` models were available on 2026-08-29; the previously-known large-capability models (`qwen3-235b`, `nemotron-3-ultra-550b`) were not in the live pool at that time (possibly throttled or temporarily unlisted), so the chain of 3 was the best available, not the best imaginable.
- **Email format preference is session-specific now** — the user's "email client does not render markdown" led to HTML inline-CSS reports. The rotator is NOT involved in the format choice (the agent sends the email). The `scheduled-email-reports` skill should note the HTML preference.
- **The rotator runs `no_agent=True`; it never uses an LLM.** The sample comparison (primary vs backup) required an explicit `cronjob action=run` with the user's prompt, not the rotator itself. Don't confuse "the rotator picks the backup" with "the backup produces the report." They are separate.
